# 每周实验开发文档

《游戏开发与计算机图形学》每周实验课的现场检查材料。每份文档只写当周（或指定阶段）实际发生的事，能追到提交号和证明文件。

## 一、周次编号

- 文件名用**教学周编号** `WEEK-XX`，不按提交次序编号。
- 基准：2026-11-04 那节课是第 8 周（`WEEK-08`），之后每周 +1（11-11 → `WEEK-09`）。
- 推算：`教学周 = 8 + (运行当周周三 − 2026-11-04) / 7 天`，结果取整数。
- 本周文件已存在时，在原文件上补充更新，保留人工填过的内容，**不另建编号**。

## 二、统计区间

| 文档 | 区间 |
| --- | --- |
| 第一份 `WEEK-08` | 阶段性汇报，覆盖建仓以来全部开发历程：2026-10-23（首个提交 `e348ad4`）到运行当天 |
| 之后各周 | 只写增量：上一份文档截止日期的次日 → 运行当天 |

阶段性汇报按里程碑阶段组织，不把提交按天拉平；附录列出区间内全部提交。

## 三、证据规范

1. 每条改动带提交号，或带一个真实存在的 `docs/proof/` 相对链接。
2. 写完后用脚本校验所有相对链接，坏链必须修掉再交。
3. 不知道的写「待填」，没验证过的写「未验证」；不编造数字、负责人、试玩结论或「试过的方案」。
4. 验证结果优先引用 `docs/proof/` 里已有的日志和测试结论，并注明日期；本次新跑的检查写清命令和实际输出。
5. 个人贡献按课程通知的五列写：`成员 | 本周具体任务 | 完成产出 | 核验依据 | 下周任务`。任务写到具体功能，产出写能打开看的东西，核验依据放提交号或 `docs/proof` 链接。小组固定 3 人，每人一行；姓名用真实姓名，git 署名写在核验依据里，不加解释性括号。
6. 历史跨度大时，阶段用表格，细节交给 `docs/proof/` 链接，不把 `README.md` 搬一遍。

## 四、文档结构

七个必备模块，缺一不可：

1. 基本信息
2. 本周目标（阶段性汇报可写「阶段目标」）
3. 开发与改进
4. 验证结果
5. 问题与决策
6. 下周计划
7. 个人贡献

另加：提交清单附录。

## 五、评分对照

本表是本地自查对照，用来确认每个必备模块都有可核对的内容；不替代课程评分表。

| 评分关注点 | 文档位置 | 自查方式 |
| --- | --- | --- |
| 周次与区间正确 | 基本信息 | 教学周编号、起止日期、首末提交号可对上 `git log` |
| 工作量与过程 | 开发与改进 + 提交清单附录 | 每条改动有提交号；附录提交数与区间一致 |
| 可运行、可复现 | 验证结果 | 引用 `docs/proof/` 日志并注明日期；本次新跑写明命令和输出 |
| 技术判断 | 问题与决策 | 决策能落到 `docs/adr/`；未解决项写明限制 |
| 计划性 | 下周计划 | 计划项来自 `TODO.md`、`docs/Priority_Backlog.md` 或未关闭的 ADR |
| 分工与协作 | 个人贡献 | 按 git 作者归并，小组 3 人每人一行 |
| 证据真实性 | 全文 | 坏链校验通过；无编造数字、负责人或试玩结论 |
