# PR 审查标准

<!-- hydrogenjr: technical-review-v1 -->

本文件规定 PR 什么情况能合并、什么情况不能，以及常驻审查者 HydrogenJr（替代原 Cursor Cloud Agent 上的 kk）怎么审。人审查也用同一套标准。改本文件走 PR，并且需要 Kyrie 本人批准。

以作者在 PR 或关联 Issue 里写明的预期行为为验收依据。检查实现、兼容性和回归。预期行为缺失或描述相互冲突时，请作者补充具体条件。

## 一、三种结论

每次审查只给一种结论：

| 结论 | 含义 | 之后 |
| --- | --- | --- |
| ✅ **Approve** | 所需检查通过，证据能支持实现符合预期，且无阻断项 | HydrogenJr 批准，守护进程核对合并条件 |
| ❌ **Request changes** | 确认有阻断项（第二节），或检查报告了可归因于改动的失败 | 指出位置、预期和实际行为，作者修改后重审 |
| 🟡 **待核验** | 必要的预期描述、检查结果或复现证据仍有缺口 | 先自行查验能取得的证据，再向作者说明具体需要补什么 |

## 二、阻断项（任何一条都不能合并）

**流程**

- B1. PR 描述缺“改了什么 / 怎么测 / 风险”中任何一项，或者只写“测过了”“没问题”这类空话。
- B2. 目标分支不是 `main`，或者和最新 `main` 有冲突（R1）。
- B3. 一个 PR 做了几件不相关的事：标题一句话概括不了全部改动，或者同时改了两个以上没有依赖关系的模块。
- B4. 手写代码超过约 800 行（素材、生成的场景、证明图片不算），又没说明为什么不拆。

**素材与许可**

- B5. 新增或替换的第三方素材（模型、贴图、音频、字体）没有在 `docs/ASSETS.md` 登记来源、许可和哈希。**如果新增模型素材没有标注来源与许可，一律按项目自建模型处理（不触发 B5/B6 阻断）。**
- B6. 第三方素材许可不明确，或者不是 CC0、CC-BY、MIT 这类允许再分发的许可；或者写着“待确认”“暂时”“先用着”（未标注来源与许可的新增模型按自建模型处理，不适用此项）。
- B7. 素材来自商业游戏、游戏资源包解包，或者从旧工程 `origin` 拷贝。
- B8. 提交了下载的原始压缩包、`third_party_sources/` 里的文件，或者没用上的素材。

**架构**（`ARCHITECTURE.md` 依赖规则）

- B9. `components/`、`weapons/`、`actors/` 读写 `RunState`，或者用绝对路径、分组去找别的系统。
- B10. `RunState` 和 `zone/` 战区控制以外的代码修改本局状态。
- B11. 增益不经过 `Stats`，直接改玩家或武器脚本。
- B12. 依赖方向反了（应该是 `ui → zone → actors → components`，反向只能用信号）。
- B13. 战区玩法代码读墙钟或调用 `randomize()`（AC-07，见 ADR 0005）。
- B14. 碰撞层直接写数字，没用 `CollisionLayers` 常量。

**文件卫生**

- B15. 提交了 `.godot/`、`export_presets.cfg`、本机绝对路径、密钥或个人信息。
- B16. 新加的 `.gd` 没有 `.gd.uid`，新加的素材没有 `.import`。
- B17. 手改了 `maps/zone_*.tscn`，或者改了 `tools/gen_zones.py` 却没重新生成（R5）。
- B18. diff 里夹着和任务无关的 `.tscn` / `.tres` 改动（编辑器自动重存产生的）。
- B19. 没说明理由就删除别人负责模块的代码或文件。

**运行**

- B20. 改动导致 R2 到 R5 出现 `FAIL`，例如导入报错、测试失败或地图和脚本不一致。检查失败时暂停批准。若失败来自环境或检查未能完成，先重试或说明还需什么证据。

下面三条不算硬阻断，但要作者回应：新逻辑没有新测试，也没说明为什么不加；代码风格和周围不一致（Tab 缩进、`snake_case`、类型标注）；新概念没写进 `GLOSSARY.md`，重要取舍没写 `docs/adr/`。作者给出合理解释，就可以 Approve。

## 三、分级检查

由 CI（`.github/workflows/pr-checks.yml`）或 HydrogenJr 在审查环境上运行 `tools/review/run_checks.sh`。脚本按改动的文件自动定级，取所有文件里最高的一级，只跑这一级需要的检查：

| 级别 | 改了哪些文件 | 跑哪些检查 |
| --- | --- | --- |
| docs | 只有 `*.md`、`docs/`、`.github/`、`.cursor/` | R1、R6 |
| assets | `assets/`、`art_source/` | 再加 R2 |
| map | `maps/`、`tools/gen_zones.py` | 再加 R5 |
| code | 其他文件（`.gd`、场景、`.tres`、`project.godot` 等） | 再加 R3、R4 |

| 编号 | 检查 | 做法 |
| --- | --- | --- |
| R1 | 能否合并 | `git merge-tree` 和 `origin/main` 试合并 |
| R2 | 导入 | `godot --headless --import`，出现报错行就失败 |
| R3 | 无界面测试 | 逐个跑 `tests/*_test.tscn`，以退出码为准 |
| R4 | 可复现 | 在同一台虚拟机上分别跑 PR 和 `origin/main` 的 `fixture_test`（`--fixed-fps 60`），比较哈希。哈希和机器有关，所以不拿文档里的数字比 |
| R5 | 地图是生成的 | 重新跑 `tools/gen_zones.py`，`maps/` 必须没有变化 |
| R6 | 文件卫生 | `.uid` / `.import` 齐全，`ASSETS.md` 已登记，许可写清楚，没有本机路径和密钥；再按依赖规则做文本匹配提示（`WARN`） |

`FAIL` 是硬失败。`WARN` 是脚本的提示，HydrogenJr 要打开对应代码确认：确实违规就按第二节阻断，是误报就在审查里说明原因。

**截图**：无显卡环境上，`*_proof.tscn` 截图还没在自动化审查环境中验证过。有画面变化的 PR 仍然要作者自己附截图。

## 四、定向检查与维护者审批

检查脚本遇到下面几种改动会提示定向检查。审查意见写明相关证据：

- `autoload/`、`project.godot`、`components/collision_layers.gd`。查调用方及场景资源，按实际影响核对信号、初始化顺序、存档兼容、输入或碰撞层。
- `ARCHITECTURE.md`、`docs/adr/`。核对改动后的契约、依赖方向及调用方与实现是否一致。
- 删除或移动文件。查资源路径、场景引用、注册表和测试，确认旧引用已更新或仍有兼容入口。
- fixture 哈希变化（R4）。指出预期变化的行为，核对差异和相关断言，并在同环境同种子复跑验证可复现性。意外变化按回归处理，证据不足时请作者补充。

`CONTRIBUTING.md`、`AGENTS.md`、本文件、`.github/`、`.cursor/` 或 `tools/review/` 的改动涉及仓库规则和审查机制，由 Kyrie 审批合并。HydrogenJr 仍给出技术结论。引入新的第三方代码或新的许可类型仍须按仓库规则获得 Kyrie 确认。

## 五、HydrogenJr 的工作方式

**触发**：Kyrie（`kyrie21z`）本人提交的常规 PR 由守护进程直接 Squash and merge。第四节列出的仓库规则和审查机制变更由维护者手动合并。其他作者打开、更新或将 PR 转为 Ready for review 时，由守护进程调用 HydrogenJr 在隔离沙箱中审查。CI 在 PR 就绪时运行检查，草稿 PR 跳过检查。

**每次审查的步骤**

1. 先读 PR 描述，检查 B1。
2. 运行 `bash tools/review/run_checks.sh origin/main`（`origin/main` 要先 fetch 到最新）。
3. **只读脚本输出的摘要。** 完整日志在对应审查日志目录，只有某一项 `FAIL` 或 `WARN` 时才看，而且只看对应日志的相关部分（`grep`、`tail -n 50`），不要整份读进来。
4. 从目标分支读取本标准及架构约束，对照 PR 或关联 Issue 的预期读 diff。沿调用方和资源引用核对影响，按第二、四节做定向检查。重审时重点读本轮改动及受影响的调用方，确认先前阻断项已解决，检查脚本整体重跑。
5. 二进制文件（`.glb`、`.blend`、图片、音频）只看文件名、大小和 `ASSETS.md` 登记，不读内容。
6. 按下面的格式发布审查结论并执行对应动作：
   - **Approve**：批准已审查的提交。守护进程在所需检查通过、当前 head 与审查一致、最新目标分支已核验，且满足仓库合并规则时执行 Squash and merge。
   - **Request changes**：发表审查评论指出阻断项，不合并。
   - **待核验**：发表评论说明未核验的行为和需要补充的证据，由 PR 作者回应。

**权限**

- 不往 PR 分支推提交，不关闭 PR，不改 Issue。需要修改的地方写成建议，由作者自己改。
- 自动合并由守护进程执行。第四节列出的仓库规则和审查机制变更走维护者审批。
- 不配置也不读取任何密钥。
- 不能确定的地方写“不确定”，不要猜。

**审查评论格式**

```
结论：Approve / Request changes / 待核验
级别：docs / assets / map / code

检查结果：（说明已核对的预期、定向检查证据，以及脚本摘要里的 FAIL、WARN 和 summary 行）

阻断项：
- B? 文件:行 —— 问题，以及要怎么改

建议项（不阻断）：
- ...

未验证：手感、画面观感，以及截图（虚拟机没有显卡）。
```

## 六、作者要做什么

- 按 `.github/pull_request_template.md` 填写。机器能跑的测试由 CI / HydrogenJr 自己跑，“怎么测”里只写**手动玩过的流程**和看到的结果。
- 有画面变化附截图。
- 开 PR 前可以自己先跑一遍检查：`GODOT=你的 godot 路径 bash tools/review/run_checks.sh`。
- 对 HydrogenJr 的意见有不同看法，在评论里回复理由。把影响验收的新预期或证据补进 PR 描述，便于重新审查。
